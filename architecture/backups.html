Backup Schedule

All backups run from the AWS app server via cron, using ~/chakra-backup/chakra-backup.sh. They go to the IMG S3 bucket under chakra-aws-backups/. The instance role can upload but not delete, so the backups are append-only.

Each successful run writes status/last-success-db.txt or last-success-files.txt; failures are logged to ~/backups-local/backup.log. A dump smaller than 1 MB is treated as broken and the run fails.

Monitoring

~/chakra-backup/chakra-health.sh runs every 5 minutes and publishes CloudWatch metrics in Chakra/Health. BackupDbFresh and BackupFilesFresh alert when a backup is overdue; they read both backup.log and the rotated backup.log.1. The full metric list is on AWS production.

One Bucket, Two Very Different Jobs

This is the single most important thing to understand about the S3 setup, and it is easy to miss: the bucket that serves live public websites is the same bucket that stores database dumps and system backups. There is no separate "public assets" bucket. The only thing separating world-readable content from backup archives is which prefix nginx is pointed at.

Actual Bucket Layout

/home/root2/s3bucket/ # s3fs mount on root2 public/ # parent of the served dirs Websites/ # SERVED - document root for faculty.iitr.ac.in ~abhaysah/ ~akrayfpt/ ... # per-faculty dirs (tilde + username) ar/ ce/ ch/ cs/ ece/ ee/ ma/ me/ ph/ ... # per-department dirs iitr.ac.in/ FacSpace/ # SERVED - under location /media/facspace/ websites/ Webspace/ # NOT referenced by nginx - dormant/legacy protected/ # NOT referenced by nginx - dormant # ── everything below is BACKUP data in the same bucket, ABOVE the served root ── chakra-aws-backups/ # current Chakra backups from the AWS server (see above) chakra-backups/ # root1-era Chakra dumps, up to Dec 2025 incremantal-backups/ # root1-era daily copies, to Jul 2026 (sic) omniport-backup/ # Omniport - a separate system omniportBackup/ # ...and two more naming variants omniport-backups/ new_dump/ 2026-05-01.tar.gz ... 2026-05-30.tar.gz # dated daily archives # stray files sitting in the bucket root cartoon.php move.py diagnose_conflicts.py beast_test remount_test.txt

Every nginx root/alias on root2 that touches this bucket points at public/Websites/ (faculty.iitr.ac.in) or public/FacSpace/ (via location /media/facspace/) - never at public/ or the bucket root. autoindex is off everywhere and protected/ is not referenced. The backup directories sit above the served root and nginx normalises .., so the backups are not reachable over HTTP through nginx.

The S3 endpoint is closed too. Anonymous requests to img-icc-bucket return 403 AccessDenied - for chakra-backups/ and chakra-aws-backups/, for an anonymous bucket listing, and for the public/Websites/ prefix. The bucket is not world-readable at its native S3 endpoint, and faculty sites are reachable only through nginx's credentialed s3fs mount, not directly. Backups are not exposed at either layer.

This reflects the current setup, not a structural guarantee: public content and backups still share one bucket. The separation would break if the bucket's public-access-block / policy were loosened, or if an nginx root were moved up a level. Neither is enforced by anything in Chakra.

Points Worth Reviewing

  • Public web server has read-write access to the backup store. The mount on edith is fuse.s3fs (rw, allow_other) over the entire bucket, backup prefixes included. So compromise of the internet-facing static server means write/delete access to Chakra and Omniport backups. Backup integrity has no storage-level protection from the web tier.
  • Backups and public content are not isolated by bucket - only by which prefix nginx serves. A bucket-level public-read policy would expose database dumps regardless of nginx.
  • Another system's backups live here too - omniport-backup* means a Chakra bucket misconfiguration is also an Omniport data exposure.
  • Three spellings of the Omniport backup directory (omniport-backup, omniportBackup, omniport-backups). Whether these are all live targets, or leftovers from renamed jobs, is unknown.
  • Two dormant sibling directories under public/: websites (lowercase) and Webspace are not referenced by any nginx block - unclear if they are stale or awaiting wiring.
  • Loose scripts in the bucket root (cartoon.php, move.py, diagnose_conflicts.py) are unowned and undocumented.
  • The s3fs mount is not in /etc/fstab - it is mounted by some other mechanism (likely a systemd .mount unit), so how it survives reboot and where its credentials live should be documented.

The mount is s3fs onto bucket img-icc-bucket in region ap-south-1, mounted -o allow_other as root. The AWS app server does not mount it; it writes backups with the AWS CLI and an instance role that can upload but not delete.

Database Backup

PostgreSQL runs in Docker container chakra-docker_database_1. Full dumps go to S3 every 6 hours.

How It Works

  1. Cron runs chakra-backup.sh db at minute 15 of every sixth hour
  2. The script runs pg_dump inside the database container and gzips the output
  3. Dumps under 1 MB fail the run; good dumps are uploaded to chakra-aws-backups/db/YYYY/MM/
  4. The server keeps the newest 7 dumps in ~/backups-local/db/ for fast restores; S3 keeps all of them

Manual Backup

# Same as the cron job; logs to ~/backups-local/backup.log ~/chakra-backup/chakra-backup.sh db

File Backup

A daily sync copies the website content and nginx configs to S3.

How It Works

  1. Cron runs chakra-backup.sh files daily at 21:30 UTC
  2. aws s3 sync copies website/XML, website/HTML, website/JoshUsers, reverse_proxy_configurations and media_files (previews excluded) under files/
  3. It runs at the lowest CPU and IO priority, and only uploads changed files

Together with the database dumps and config snapshots, this is everything needed to rebuild the app server from scratch.

Live Content Redundancy

Published content has natural redundancy through the lsyncd architecture:

Recovery scenario: If root2 fails, set up a new server, open the reverse tunnel and let lsyncd resync. If the app server fails, restore the latest database dump, the files/ sync and the newest config snapshot onto a new instance.

History: when root1 failed in November 2026, the newest database copy was a January dump, and the published XML had to be reconciled with root2's live HTML. The 6-hourly dumps exist so that does not happen again.

What's NOT Backed Up

  • Preview images (media_files/preview/) - temporary, regenerated on every preview; excluded from the file backup
  • Docker volumes (except the database) - the static_backend volume is regenerated by collectstatic
  • RabbitMQ state - the message queue is transient
  • Memcached - in-memory cache, no persistence needed
  • Web server logs - kept on the server's filesystem only
