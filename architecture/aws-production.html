Publishing path to root2

lsyncd (lsyncd-chakra systemd unit, /etc/lsyncd/lsyncd.conf.lua) pushes five streams to root2 through a reverse SSH tunnel that root2 keeps open from cron. All streams use delete = true.

  • Short URLs: the AWS directory reverse_proxy_configurations/shorturls/ is a full mirror of root2's /etc/nginx/conf.d/includes/, hand-written files such as main-route.conf included. Edit those files on AWS, never on root2: lsyncd overwrites root2 from AWS, and a file deleted on AWS is deleted on root2.
  • Short-URL generation: approving a faculty short URL queues the Celery task create_shorturl_configuration, which rewrites every subdomain's file from the database.

Server-only configuration is locked

Secrets and environment-specific files are not in git, so a deploy or a build script (for example scripts/build/postgres.sh, which can regenerate database.env) must never change them. ~/chakra-env-guard.sh snapshots them, makes them immutable (chattr +i) and checks them for drift.

Secrets that must agree

  • Transpiler token: the backend's compose command runs source chakra_backend/.env, so $ in a value is shell-expanded. The value the web workers see is what chakra-core/.env must hold. Compare against /proc/<gunicorn pid>/environ, not against manage.py shell, which reads the file unexpanded. chakra-core-start.sh reads its .env literally.
  • Broker login: RABBITMQ_DEFAULT_USER and RABBITMQ_DEFAULT_PASS in the backend .env must match rabbitmq/message_broker.env, otherwise Celery's login is refused and the worker exits.

Deploying

Normal path: Jenkins. The canvas-chakra-backend, canvas-chakra-frontend, canvas-chakra-core and canvas-chakra-library jobs on lupin run on every push to master (library: staging): they git pull --rebase over SSH and restart the container or rebuild the transpiler, so a merged PR is live within about a minute. Check it with the smoke test below instead of deploying again. The core checkout marks components.json skip-worktree so its local LibraryConfig does not block the pull.

Fallback without Jenkins: the server has no GitHub credentials for the private repositories. Ship commits as a git bundle and fast-forward. Never git clean -x a checkout: it would delete ignored files such as .env (the lock blocks it, but the guard is not a reason to try).

After every deploy or restart run bash scripts/smoke.sh from ~/chakra-docker. It renders a real preview through the transpiler with the web workers' environment, pings Celery and checks the config guard; any FAIL line means the deploy is not done.

The production image is Python 3.8. CI runs compile and unit tests on 3.8, so a 3.9+ only API fails in CI instead of at import time on the server.

Health and backups

  • ~/chakra-backup/chakra-health.sh runs every 5 minutes and publishes CloudWatch metrics in Chakra/Health: BackupDbFresh, BackupFilesFresh, DiskOk, LsyncdUp, Root2TunnelUp, BackendUp, FrontendUp, TranspilerUp, SiteUp, ConfigUnchanged, CeleryUp and AllOk. Backup freshness reads both backup.log and backup.log.1, since logrotate empties the log daily.
  • ~/chakra-backup/chakra-backup.sh db|files uploads database dumps (every 6 hours) and files (daily) to the IMG S3 bucket under chakra-aws-backups/. Config snapshots go to chakra-aws-backups/env/.
