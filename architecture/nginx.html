Nginx & Routing

Two nginx instances - the editor proxy on the AWS app server, the public static server on root2

Two Nginx Instances

Chakra uses two separate nginx instances. The one on the AWS app server proxies the editor and its API at chakra.channeli.in. The one on root2 (edith) serves the published websites (iitr.ac.in and every subdomain) as static files. Server access details are in the private chakra-ops skill (chakra-backend/.claude/skills/chakra-ops).

AWS Nginx — chakra.channeli.in

This is the host nginx, not a container. Site file: /etc/nginx/sites-enabled/chakra.conf, with includes in /etc/nginx/conf.d/includes/. The copies under chakra-docker/nginx/ in the repo are templates and are not loaded. The live files are locked by the config guard (see AWS production).

  • Listens on 443 with TLS 1.2/1.3 and HTTP/2.
  • Editor is IITR-network only: iitr-only.conf allows the campus range and localhost (for health checks) and denies everything else.
  • canvas.channeli.in (the old name) answers 410 Gone with X-Robots-Tag: noindex.
  • Any other name or a bare IP hits a default server that closes the connection (444).

Upstream Definitions

All upstreams bind to 127.0.0.1 because the containers run with network_mode: host. The transpiler (Flask on :5000) is called by the backend directly and is not exposed through nginx.

# /etc/nginx/conf.d/includes/upstreams.conf upstream gunicorn { server 127.0.0.1:8000; } upstream daphne { server 127.0.0.1:8001; } upstream next { server 127.0.0.1:3000; }

Root2 Nginx — Public Websites

root2 loads only what /etc/nginx/nginx.conf includes. sites-enabled/ is not loaded, so files there have no effect.

The subdomains/, josh-subdomains/ and short-URL files arrive from the AWS app server through lsyncd. A systemd service on root2 (hot-nginx-reload) watches /etc/nginx/ with inotifywait and reloads nginx when they change.

Per-Subdomain Server Block

# sites-available/subdomains/ece.conf (trimmed) server { listen 443 ssl; server_name .ece.iitr.ac.in; root '/home/root2/new_website/Departments/Electronics and Communication Engineering Department'; ssl_certificate /certificates/iitr-certificate/ssl.cert; include conf.d/includes/compression.conf; include conf.d/includes/ece.conf; # short URLs for this subdomain location / { index 'Home.html'; } }

Every site root, and the main site, has a favicon.ico (the IITR emblem) unless the site ships its own.

Short URLs (faculty profiles)

Short URLs live in conf.d/includes/<subdomain>.conf (one per subdomain) and iitr.conf (for iitr.ac.in). Each maps a friendly path to a published HTML file:

# conf.d/includes/ee.conf location = "/~EE/manojfee" { default_type "text/html"; alias '/home/root2/new_website/Departments/Electrical Engineering Department/People/Faculty/100571.html'; }

This directory is a full mirror of the ConfMan output on AWS (delete = true), so a hand edit on root2 is overwritten. Change short URLs through ConfMan.

Faculty Personal Websites (faculty.iitr.ac.in)

faculty.iitr.ac.in is the one subdomain that does not serve content produced by the Chakra CMS pipeline. It has no XML source, no transpiler step and no lsyncd stream. Instead nginx serves it straight off the S3 mount, where faculty maintain their own files:

root /home/root2/s3bucket/public/Websites/$dep/$fac;

Content is organised two ways under public/Websites/: per-faculty directories named ~username (e.g. ~abhaysah), and per-department directories (ece, ce, ma, ...).

Important: this S3 bucket is the same bucket that holds Chakra database dumps and Omniport backups. nginx is pointed at the public/ prefix only, which is what keeps the backup directories off the web - see Backups & S3 for the full bucket layout and the risks that come with it.

Proxy Rules on Root2

root2 serves static files only; it does not call back into the app server. The few proxy_pass rules left are in conf.d/includes/faculty-website-route.conf:

  • a handful of old faculty pages proxied to a legacy internal web server;
  • one external Google Sites page;
  • /favicon.ico on faculty routes, proxied to https://iitr.ac.in/favicon.ico.

Rate Limiting

AWS nginx defines two zones per client IP. The zone names still carry the old canvas prefix.

# /etc/nginx/sites-enabled/chakra.conf limit_req_zone $binary_remote_addr zone=canvas_zone:16m rate=16r/s; limit_req_zone $binary_remote_addr zone=canvas_api_zone:16m rate=300r/s;
