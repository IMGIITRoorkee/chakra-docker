How Chakra Works

Chakra is a Component Content Management System (CCMS). Instead of writing HTML, editors compose pages from pre-built UI components (sliders, cards, tables, etc.) in a visual editor. The system stores these as XML, then converts them to static HTML for delivery.

The Pipeline

  1. Edit - Editor uses the Next.js frontend at chakra.channeli.in to compose a page from components
  2. Save - Component tree saved as an XML draft (<page>.xml.draft) in website/XML/
  3. Preview - Transpiler converts the draft to HTML in memory and returns it to the browser
  4. Publish - Draft becomes <page>.xml; the transpiler writes HTML to website/HTML/
  5. Sync - lsyncd pushes the HTML to root2 with rsync over a reverse SSH tunnel
  6. Serve - nginx on root2 serves the static HTML to the public

Two-Server Architecture

Production runs on two servers. The AWS app server runs Chakra itself; root2 (edith) on the IITR network serves the public sites. They are connected by lsyncd, a daemon on the AWS server that watches directories and rsyncs changes to root2 within seconds. Because AWS cannot open connections into the campus network, root2 keeps a reverse SSH tunnel open to AWS and lsyncd sends through it. History: until 12 November 2026 the app server was root1 (bifrost) on campus.

AWS app server (chakra.channeli.in)

Application server. Runs all logic, stores all source data. Ubuntu 18.04, 16 vCPU, 31 GB RAM, 194 GB disk.

  • Docker containers: Django backend, Next.js frontend, PostgreSQL, Memcached, RabbitMQ
  • Host processes: Flask + chakra-core (tmux), lsyncd (systemd), nginx
  • Filesystem: website/ (XML + HTML + JoshUsers), media_files/, reverse proxy configs
  • Cron: database dump every 6 hours, file backup daily, health check every 5 minutes (S3 and CloudWatch)
  • Access: editor reachable only from the IITR network

root2 / edith

Static file server. Serves published websites to the public. No app logic. Ubuntu 20.04, nginx 1.18.

  • nginx: iitr.ac.in plus 38 department and centre configs and 29 Josh site configs
  • inotifywait: hot-nginx-reload service watches /etc/nginx/, runs nginx -t and reloads on success
  • Filesystem: /home/root2/new_website/ (87 GB, synced from AWS)
  • Reverse tunnel: aws-tunnel.sh from cron (at boot and every 5 minutes) keeps the tunnel to AWS open
  • S3 mount: faculty.iitr.ac.in personal sites are served from s3bucket/public/Websites/

lsyncd Sync Streams

Configured at /etc/lsyncd/lsyncd.conf.lua on the AWS server, run by the lsyncd-chakra systemd unit. Every stream uses delete = true: a file removed on AWS is removed on root2, and a file that exists only on root2 inside a synced tree is deleted. Details on lsyncd & Sync.

The Transpiler (chakra-core)

A Scala binary wrapped in a Flask API. Converts XML component trees to static HTML using rules from components.json.

How It Runs

  • Location: ~/chakra-docker/codebase/chakra-core/ on the AWS server
  • Process: Flask on 127.0.0.1:5000 in tmux session chakra-core, started by ~/chakra-core-start.sh
  • Binary: built with pack.sh into target/universal
  • Config: components.json (320+ component definitions)

Django POSTs to http://127.0.0.1:5000/ with a shared token. Flask decodes params, runs the Scala binary as a subprocess, returns stdout (preview) or writes to disk (publish).

Process Management

Inside the Django Docker container, supervisord manages three processes (program list in supervisor.d/supervisord.conf):

HTTP

Gunicorn

3 workers, gthread, 120s timeout. Handles all Django REST API traffic on port 8000.

WS

Daphne

ASGI server for WebSocket connections on port 8001. Real-time features.

BG

Celery

Background task worker with autorestart. Consumes from RabbitMQ: short-URL config generation, mail, unindexing.

Scheduled Jobs

The backend declares two django-crontab jobs in settings.CRONJOBS. The current image has no cron daemon, so neither runs on the AWS server; preview images in media_files/preview are not cleaned up (1286 files, 1.4 GB on 15 November 2026).
