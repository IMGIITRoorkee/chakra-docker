One Bucket, Two Very Different Jobs

This is the single most important thing to understand about the S3 setup, and it is easy to miss: the bucket that serves live public websites is the same bucket that stores database dumps and system backups. There is no separate "public assets" bucket. The only thing separating world-readable content from backup archives is which prefix nginx is pointed at.

Actual Bucket Layout

/home/root2/s3bucket/ # also mounted at /home/root1/s3bucket public/ # parent of the served dirs Websites/ # SERVED - document root for faculty.iitr.ac.in ~abhaysah/ ~akrayfpt/ ... # per-faculty dirs (tilde + username) ar/ ce/ ch/ cs/ ece/ ee/ ma/ me/ ph/ ... # per-department dirs iitr.ac.in/ FacSpace/ # SERVED - under location /media/facspace/ websites/ Webspace/ # NOT referenced by nginx - dormant/legacy protected/ # NOT referenced by nginx - dormant # ── everything below is BACKUP data in the same bucket, ABOVE the served root ── chakra-backups/ # Chakra PostgreSQL dumps incremantal-backups/ # daily incrementals (sic) omniport-backup/ # Omniport - a separate system omniportBackup/ # ...and two more naming variants omniport-backups/ new_dump/ 2026-05-01.tar.gz ... 2026-05-30.tar.gz # dated daily archives # stray files sitting in the bucket root cartoon.php move.py diagnose_conflicts.py beast_test remount_test.txt

Every nginx root/alias on root2 that touches this bucket points at public/Websites/ (faculty.iitr.ac.in) or public/FacSpace/ (via location /media/facspace/) - never at public/ or the bucket root. autoindex is off everywhere and protected/ is not referenced. The backup directories sit above the served root and nginx normalises .., so the backups are not reachable over HTTP through nginx.

The S3 endpoint is closed too. Anonymous requests to img-icc-bucket return 403 AccessDenied - for chakra-backups/, for an anonymous bucket listing, and for the public/Websites/ prefix. The bucket is not world-readable at its native S3 endpoint, and faculty sites are reachable only through nginx's credentialed s3fs mount, not directly. Backups are not exposed at either layer.

This reflects the current setup, not a structural guarantee: public content and backups still share one bucket. The separation would break if the bucket's public-access-block / policy were loosened, or if an nginx root were moved up a level. Neither is enforced by anything in Chakra.

Points Worth Reviewing

  • Public web server has read-write access to the backup store. The mount on edith is fuse.s3fs (rw, allow_other) over the entire bucket, backup prefixes included. So compromise of the internet-facing static server means write/delete access to Chakra and Omniport backups. Backup integrity has no storage-level protection from the web tier.
  • Backups and public content are not isolated by bucket - only by which prefix nginx serves. A bucket-level public-read policy would expose database dumps regardless of nginx.
  • Another system's backups live here too - omniport-backup* means a Chakra bucket misconfiguration is also an Omniport data exposure.
  • Three spellings of the Omniport backup directory (omniport-backup, omniportBackup, omniport-backups). Whether these are all live targets, or leftovers from renamed jobs, is unknown.
  • Two dormant sibling directories under public/: websites (lowercase) and Webspace are not referenced by any nginx block - unclear if they are stale or awaiting wiring.
  • Loose scripts in the bucket root (cartoon.php, move.py, diagnose_conflicts.py) are unowned and undocumented.
  • The s3fs mount is not in /etc/fstab - it is mounted by some other mechanism (likely a systemd .mount unit), so how it survives reboot and where its credentials live should be documented.

The mount is s3fs onto bucket img-icc-bucket in region ap-south-1, mounted -o allow_other as root. Both root1 and root2 mount this same bucket.

Database Backup

PostgreSQL runs in Docker container chakra-docker_database_1. Weekly full dumps are stored in S3.

How It Works

  1. Cron triggers /home/root1/database_backup.sh on Sunday midnight
  2. Script runs pg_dump inside the Docker container
  3. Dump file is written to the S3 mount at /home/root1/s3bucket/chakra-backups/
  4. Old backups are retained (no automatic rotation observed)

Manual Backup

# Run pg_dump inside the database container docker exec chakra-docker_database_1 \ pg_dump -U postgres chakradb > backup_$(date +%Y%m%d).sql

Incremental Backup

Daily incremental backups capture changed files across the codebase and website content.

How It Works

  1. Cron triggers /home/root1/incremental_backup_to_aws_script.sh daily at 3 AM
  2. Script syncs changed files to S3 mount
  3. Output suppressed (> /dev/null 2>&1)

The incremental backup covers the website content, media files, and configuration — everything needed to restore root1 from scratch.

Recovery scenario: If root2 fails, replace it with a fresh server, configure lsyncd target, and wait for a full sync. If root1 fails, restore from S3 backups (database dump + incremental files).

What's NOT Backed Up

  • Preview images (media_files/preview/) — ephemeral, regenerated on demand, cleaned hourly
  • Docker volumes (except database) — static_backend volume is regenerated by collectstatic
  • RabbitMQ state — message queue is transient, Celery tasks are idempotent
  • Memcached — in-memory cache, no persistence needed
  • Web server logs — retained on root1's filesystem but not backed up to S3
