Transpiler (chakra-core)

Scala binary behind a Flask API on the AWS app server - converts XML component trees to static HTML

How It Runs

The transpiler is a Scala binary wrapped in a small Flask API (Python 3.6 virtualenv). It runs on the host, not in Docker, inside the tmux session chakra-core.

Runtime Details

  • Checkout: ~/chakra-docker/codebase/chakra-core/
  • Start script: ~/chakra-core-start.sh reads .env literally, activates chakra-core-env, then runs flask run --host=127.0.0.1 --port=5000
  • Binary: target/universal/chakra-core-0.2.0-SNAPSHOT/bin/chakra-core, built by pack.sh
  • Config: components.json (80 component definitions plus LibraryConfig)
  • Environment: SECRET_FLASK and CODEBASE_PATH in the locked .env

The start script must not source the .env: SECRET_FLASK contains $, and shell expansion would change it, so every render would fail with "Invalid token". Restart commands are in the private chakra-ops skill.

Flask Endpoints

MethodPathPurpose
POST/Main transpiler: converts XML to HTML (also accepts GET; anything without a valid token gets a 500)
GET/healthLiveness check
GET/health/readyReadiness: checks CODEBASE_PATH is set and exists

The 5-minute health script calls /health; scripts/smoke.sh calls /health/ready and also renders a real page.

Django Integration

Django (generator/utils/transpiler.py) POSTs to SERVER_URL (http://127.0.0.1:5000/). Flask checks the token with a constant-time compare, builds the command line and runs the Scala binary as a subprocess in transpiler_path.

Constructed CLI Command

./chakra-core --write-stdout -i {input_path} -c {components.json} -m {menu} [--header ...] [--footer ...]

Input and output paths are resolved against CODEBASE_PATH and rejected if they fall outside it.

components.json

Each component definition lists its CSS classes, JS files and allowed children. The LibraryConfig block holds the server-specific hosts, so the server copy differs from git: it is marked skip-worktree and drift-checked by the config guard (a locked copy lives at ~/chakra-core-libraryconfig.json).

Asset Configuration

"assets_host": "https://chakra.channeli.in/media/preview" "dummy_assets_host": "./assets" "chakra_base_url": "https://chakra.channeli.in"

ImageSpec.scala chooses between the two hosts. In preview mode it replaces "./assets" with assets_host in Image and FluidImage src attributes. The file is read on every call, so a change takes effect without a restart.

These hosts must name the current editor host. When the editor moved from canvas.channeli.in, an old assets_host left every preview image returning 410.

Preview vs Publish

The transpiler operates in two distinct modes depending on how it is invoked by Django.

Preview Mode

  • Flag: --write-stdout
  • replaceAssets: true
  • Image paths: Absolute URLs (https://chakra.channeli.in/media/preview)
  • Output: HTML string returned to Django, sent to browser

Publish Mode

  • Flag: -o {output_path}
  • replaceAssets: false
  • Image paths: Relative ./assets
  • Output: HTML file written to disk at output path

Building and Deploying

The Scala code is built with sbt. pack.sh runs sbt dist and unpacks the result into target/universal/chakra-core-0.2.0-SNAPSHOT/.

# In the core checkout on the AWS app server ./pack.sh

Flask starts the binary as a new process on every call, so a rebuilt binary is used immediately. Restart the tmux session only when app.py, its dependencies or the .env change. Jenkins (canvas-chakra-core) pulls and rebuilds on every merge to master; then run scripts/smoke.sh. See Deployment.
