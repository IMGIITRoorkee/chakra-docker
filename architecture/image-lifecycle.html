Upload

User uploads an image via the editor. The backend hashes the page PK to namespace the file, then writes it to the XML node's assets directory.

Request

# Endpoint POST /api/generator/image/ # Filename generation (Python) filename = sha256( str(xml_page_pk).encode('utf-8') ).hexdigest() + "_" + original_name

Result

AspectDetail
Written towebsite/XML/{node}/assets/{filename}
Response{ value: "./assets/{filename}", key: original_name }
SyncFile lives ONLY on root1. Not synced to root2.

Key point: The website/XML/ directory is never synced by lsyncd. Upload artifacts exist only on the application server until publish.

Preview

When an editor previews a page, Django calls the Flask transpiler with write_stdout=True and rewrites image paths to absolute URLs so the browser can fetch them from root1.

Flow

  1. Request: GET /api/generator/preview/?xml_page_pk=123
  2. Django → Flask: Calls transpiler on localhost:5000 with write_stdout=True
  3. Transpiler: ImageSpec.scala sets replaceAssets=true, replaces "./assets" → "https://chakra.channeli.in/media/preview"
  4. Django: Copies matching images from website/XML/{node}/assets/ → media_files/preview/
  5. Response: Returns HTML with absolute preview URLs

Preview images are temporary. They are served directly from root1 via chakra.channeli.in/media/preview and never reach root2.

Publish

Publishing converts XML to HTML on disk and copies image assets alongside the HTML. After lsyncd syncs, the image exists in three places.

Publish Steps

  1. XMLPage.publish() in generator/models/page.py
  2. Calls transpiler with write_stdout=False → writes HTML to website/HTML/{node}/
  3. replaceAssets stays false → HTML retains relative "./assets" paths
  4. Django copies images: website/XML/{node}/assets/ → website/HTML/{node}/assets/
  5. lsyncd detects changes → rsyncs HTML + assets to root2

Three Copies After Publish

#LocationServerPurpose

Key Code Reference

# generator/models/page.py — publish method (around line 219-237) # 1. Call transpiler (write to disk) # 2. Copy assets from XML dir to HTML dir # 3. lsyncd handles sync to root2 automatically

Serving

Public users never interact with root1. Their browser loads static HTML from root2, and images resolve via relative paths.

Request Flow

  1. User visits cec.iitr.ac.in/page.html
  2. root2 nginx serves from /home/root2/new_website/
  3. HTML contains relative ./assets paths
  4. Browser resolves to same directory on root2
  5. nginx serves the image from root2's filesystem

Why Relative Paths Work

The published HTML file and its assets/ folder are siblings in the same directory. When the browser encounters ./assets/photo.png in the HTML, it resolves relative to the page URL, which maps to the same directory on root2's filesystem.

# Directory structure on root2 /home/root2/new_website/cec/ page.html # <img src="./assets/photo.png"> assets/ abc123_photo.png # served by nginx

Listing (Frontend Image Picker)

The editor's image picker fetches a list of images already uploaded to the current page's XML node.

Request

# Endpoint GET /api/generator/image?xml_page_pk=123

Django scans the XML node's assets/ directory and filters files by the SHA-256 prefix derived from the page PK. Only images belonging to this page are returned.

Response

Returns a list for the image picker dropdown, allowing editors to re-use previously uploaded images without re-uploading.

Why prefix filtering matters: Multiple pages within the same XML node share the assets/ directory. The SHA-256 prefix ensures each page only sees its own uploads.

Deletion

Image deletion only removes the file from the XML source. Published copies persist until the page is re-published.

Request

# Endpoint DELETE /api/generator/image?xml_page_pk=123 &image_name=photo.png

What Gets Deleted

Caveat: If an image is deleted and the page is never re-published, the old image remains accessible on the public site indefinitely.
