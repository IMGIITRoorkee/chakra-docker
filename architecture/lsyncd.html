lsyncd & Sync

Live Syncing Daemon — continuous rsync on file changes from root1 to root2

What is lsyncd?

lsyncd (Live Syncing Daemon) watches directories on root1 for file changes and triggers rsync to push those changes to root2 in near-real-time. It is the backbone of the two-server architecture — ensuring published content and nginx configs reach the static file server automatically.

Configuration

  • Config file: /etc/lsyncd/lsyncd.conf.lua on root1
  • Mode: default.rsync
  • SSH key: /home/root1/.ssh/website-key
  • Known hosts: Specified in config for strict host checking

Logging

  • Log file: /var/log/lsyncd/lsyncd.log
  • Status file: /var/log/lsyncd/lsyncd.status

5 Sync Streams

lsyncd maintains 5 independent sync streams, each watching a different directory on root1 and pushing changes to a corresponding directory on root2.

#Source (root1)Target (root2)What Syncs
1website/HTML//home/root2/new_website/Published pages + assets/ folders
2website/JoshUsers//home/root2/new_website/Josh Users/Josh user websites
3reverse_proxy_configurations/subdomains//etc/nginx/sites-available/subdomains/Subdomain nginx server block configs
4reverse_proxy_configurations/shorturls//etc/nginx/conf.d/includes/Short URL location blocks
5reverse_proxy_configurations/josh-subdomains//etc/nginx/sites-available/josh-subdomains/Josh subdomain configs

What Does NOT Sync

Not everything on root1 is pushed to root2. Several directories and resources stay on root1 only.

ResourceLocationWhy Not Synced
website/XML/root1 onlySource XML is only needed for editing and transpilation, not serving
media_files/root1 onlyPreview images served directly from root1 via chakra.channeli.in/media
PostgreSQL databaseroot1 Docker volumeApplication database only needed by Django on root1
Docker volumesroot1 onlyNo Docker containers run on root2

Key insight: Only published HTML reaches root2. Preview images are served from root1 directly via chakra.channeli.in.

Auto-Reload on root2 (inotifywait)

When lsyncd pushes new nginx configs to root2, they need to take effect without manual intervention. This is handled by inotifywait.

# On root2: watches for nginx config changes inotifywait --monitor --recursive /etc/nginx/ → hot-nginx-reload.sh → nginx -s reload

The inotifywait process watches /etc/nginx/ recursively. When any file is created, modified, or deleted, it triggers hot-nginx-reload.sh, which runs nginx -s reload to apply the new configuration without downtime.

Configuration Example

Each sync stream in lsyncd.conf.lua follows this pattern:

-- /etc/lsyncd/lsyncd.conf.lua settings { logfile = "/var/log/lsyncd/lsyncd.log", statusFile = "/var/log/lsyncd/lsyncd.status", } sync { default.rsync, source = "/path/to/source/", target = "root2@192.168.121.188:/path/to/target/", rsync = { rsh = "/usr/bin/ssh -i /home/root1/.ssh/website-key", } }

Troubleshooting

When files are not reaching root2 as expected, check these common issues:

CheckCommand / ActionWhat to Look For
lsyncd logtail -f /var/log/lsyncd/lsyncd.logErrors, connection failures, permission denied messages
SSH key permissionsls -la /home/root1/.ssh/website-keyShould be 600 (owner read/write only)
Manual rsync testrsync -avz -e "ssh -i /home/root1/.ssh/website-key" source/ target/Verify rsync works independently of lsyncd
lsyncd statuscat /var/log/lsyncd/lsyncd.statusNumber of pending syncs, last sync timestamps
lsyncd processsystemctl status lsyncdIs the daemon running?
