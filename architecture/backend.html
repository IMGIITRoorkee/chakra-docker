Backend (Django)

Django application server on the AWS app server - APIs, auth, file management and the publish workflow

Container Overview

The backend runs in the chakra-docker_chakra-backend_1 container (image chakra-backend:latest, Python 3.8, network_mode: host). Inside it, supervisord runs three processes: HTTP, WebSocket and background tasks. The checkout is ~/chakra-docker/codebase/chakra-backend; Jenkins pulls it and restarts the container when master changes (see Deployment).

Startup Command

source chakra_backend/.env && supervisord -c /supervisord.conf

Because the .env is sourced by bash, any value containing $ is shell-expanded before Django sees it. That matters for SECRET_FLASK, which must match the transpiler (see AWS production, "Secrets that must agree").

Process Management (supervisord)

Config: supervisor.d/supervisord.conf in the checkout. It is server-specific and locked against changes by the config guard.

HTTP

Gunicorn

Port 8000, 3 workers. Serves the Django REST API and admin.

WS

Daphne

Port 8001. ASGI server for WebSocket connections.

BG

Celery

Worker with autorestart=true. Broker: the RabbitMQ container on localhost:5672. Runs short-URL config generation, Hindi conversion and search index updates.

History: until November 2026 Celery never ran on this server, because the broker credentials were missing from the .env and the worker exited cleanly without a restart. The credentials must match rabbitmq/message_broker.env.

Saving a page

Saves write <page>.xml.draft next to the published <page>.xml. Creating the draft row and writing the file happen in one database transaction, so a failed save leaves no draft row pointing at a missing file. Empty links (link="") pass validation. Publishing is described in Image Lifecycle.

URL Routing

The host nginx on the AWS app server routes requests by URL prefix. The editor calls the API as /api/...; Next.js rewrites that to the backend. Full table on the Nginx page.

URL PatternDestinationProcess
/chakra_auth, /generator, /filemanager, /confman, /adminDjango viewsGunicorn :8000
/wsASGI consumersDaphne :8001
/api/*Next.js rewrite to the backendNext.js :3000, then Gunicorn

Scheduled Jobs

Two jobs are declared in settings.CRONJOBS through django-crontab:

ScheduleFunctionPurpose
Every 60 mingenerator.cron.my_scheduled_jobRuns tmp_clear.sh - deletes preview images older than 1 day
Every 720 mingenerator.cron.notice_list_publish_cronAuto-publishes notice list pages

Known gap: django-crontab installs jobs into the system crontab, and the backend image has no cron. Neither job runs on the AWS app server, so preview images accumulate and notice lists are republished only by hand.

Logging

Logs are written to /web_server_logs/ inside the container, bind-mounted to web_server_logs/ in the checkout.

Log FileSource
supervisord_logs/gunicorn-stderr.logDjango errors and tracebacks (the first place to look for a 500)
supervisord_logs/daphne-*.log, daphne_logs/access.logDaphne WebSocket server
supervisord_logs/celery-*.logCelery worker
django.log, generator.logApplication loggers

Request logs for the editor are in the host nginx logs. One-off maintenance scripts and their backups (republish runs, dry-run results) are also kept in web_server_logs/.
